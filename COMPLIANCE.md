# Spec compliance — meister

Status: version 0.2.0 (Rung 1 — Scaffolding and canon, plan of
record README.md).
Basis: stdio behaviour below is exercised by the in-repo suites
(unit, stdio conformance, manifest agreement) run on primo at
the Rung 1 gate; per-client tolerance (MCP Inspector, rose,
phlow) has NOT been run at this rung and is not claimed.

## 1. Lifecycle and version negotiation

Modern era only. The server pins `supported_protocol_versions`
to `2026-07-28` and is stateless and discover-first: clients use
`server/discover`, `tools/list`, and `tools/call`, each carrying
the modern-era `_meta` probe (`io.modelcontextprotocol/
protocolVersion`). A stdio era guard owns the transport end:
`initialize` is refused with a typed protocol error `-32022`
naming 2026-07-28, and `tools/list` without the `_meta` probe is
refused the same way. Stateless operation: no session state is
kept; the guard forwards only discover, ping, tools/list, and
tools/call. Since Rung 1 the server holds an on-disk record
store (§3, §7) — records persist between sessions; dispatch
itself keeps no session state.

## 2. Transport — stdio

JSON-RPC over stdio, one JSON object per line, 4 MiB line bound.
Notifications (requests without an id) are dropped unexecuted.
Parse errors answer `-32700`; unknown methods `-32601`;
oversized lines `-32600`. Stderr is diagnostics only; stdout
carries protocol frames only.

Profile selection (EFLO-03). One profile is served per launch,
chosen by `MEISTER_PROFILE` (§7); unset selects `core`.
`tools/list` carries only the selected profile's tools. A
`tools/call` to a catalog tool outside the profile is an
`isError` result with code `group_not_loaded`, naming the tool,
the active profile, and the profiles that carry the tool (every
carrier except `full`, which is audit-only) — it is never
answered as an unknown tool. The lane gate runs BEFORE the
profile check (§4): an out-of-profile record-carrying call with
a refused envelope gets the lane code, and is never told where
the tool lives. `group_not_loaded` is pre-mutation: it returns
before the store is resolved. A profile grants no authority —
it decides what can load; the lane gate and the handlers decide
what is permitted. The conformance suite launches every
declared profile and pins its served set.

## 4. Lane law enforcement

The gate is live from this commit (`src/lane.rs`). Every
record-carrying input is an envelope (`record_id`,
`origin_lane`, `content_label`, `evidence`); the gate runs
before any handler logic and before any mutation:

- nsfw label → typed refusal `lane_mismatch`, any origin;
- non-sfw label or an sfw label claiming `origin_lane: ntranch`
  → `lane_mismatch` (records never cross lanes, either way);
- missing/unreadable label or origin, unrecognised values, or
  missing evidence → `lane_unclassified`;
- only qompass + sfw + evidence proceeds (to the handler;
  Groups 1–2 handlers are live since Rung 1, the rest are
  seams naming their rung).

Refusals are `isError` tool results whose structured body names
the offending record ids. The envelope's `content_label` is
deliberately not a schema enum: the gate owns classification, so
a bad label reaches the gate and is refused with a lane code
rather than dying as a protocol error. `meister_lane_check`
returns the gate's verdict for a candidate envelope and stores
nothing. No tool declares a visual or audio PASS; the Owner's
eye/ear are the verdict (D-713/D-221).

## 5. Errors

Execution failures are tool results (`isError` + structured
JSON: lane refusals, `not_implemented` seams, `group_not_loaded`
for a catalog tool outside the launched profile, `unknown_tool`);
protocol errors are reserved for protocol faults (era refusal,
unknown method, malformed JSON, oversized line). A client can
therefore always distinguish "the server refused this work" from
"the request was not protocol".

Since Rung 1 the store adds its own typed codes, same shape:
`invalid_input` (malformed call arguments, bad ids),
`invalid_record` (a record or lock violating the canon
governance or lock contract), `not_found`, `conflict` (a
duplicate create, never an overwrite), `identity_lock_conflict`
(a different lock over a locked character), `canon_unverified`
(the census failed closed; the full census rides in the error
body), and `io`.

store lock within its bound (§7). Nothing is written; the call
can simply be repeated.

claim, so `checked` does not change.

## 7. Security posture

No secrets are read, stored, or served: group 10 manages
credential REFERENCES and status by schema design (a
`credential_ref` string pattern, never a value), and the server
takes no CLI arguments. Since Rung 1 the server holds a record
store on disk: the root is `MEISTER_PROJECTS_ROOT` when set,
else `$XDG_DATA_HOME/meister/projects`, else
`$HOME/.local/share/meister/projects`. The server reads exactly
two environment inputs: that store root, and `MEISTER_PROFILE`,
the surface profile served for the life of the process (§3).
The `MEISTER_PROFILE` contract: unset selects `core`; a set
value must be the exact name of a declared profile (`core`,
`canon`, `systems`, `narrative`, `assets`, `qa`, `release`,
`niflheim-floor`, `full`). Any other value — empty, mis-cased,
padded, a list, not UTF-8 — makes the server refuse to start:
exit status 2, nothing written to stdout, and one typed line on
stderr (`meister: refusing to start: unknown_profile: …`)
naming the declared profiles. There is no fallback to the
default. The profile narrows the served surface only; it is not
a permission and reads no secret. Writes are confined to the
store root: record ids
are validated slugs (no path traversal), records are written
atomically (temp + rename) only after full validation, and all
reads are bounded (1 MiB per record, 32 MiB per census source).
The store holds project and cast records only — no credentials,
no media bytes (media is referenced by path + SHA-256, never
copied). The conformance suite asserts refused and seam calls
write nothing, in the working directory or the store root.

Store lock (STORE-01). Several Meister processes — one per
surface profile — can share one store root, so every mutation
holds two locks: the in-process mutex, and an exclusive advisory
`flock` on `<root>/.meister.lock`. The wait for both together
is bounded at 10 s; past it the call answers `store_busy` (§5)
and writes nothing. The lock file is infrastructure, not a
record: zero bytes, never read, never removed, and outside the
id space (ids cannot begin with a dot). Every validation for a
mutation runs once before the lock and again under it, so a
refused call leaves the store byte-identical — it does not even
create the lock file. Reads take no lock: records land by atomic
rename, so a reader sees the old record or the new one. The lock
is advisory: it excludes Meister processes from each other, not
a foreign writer that ignores it. `tests/store_lock.rs` drives
it through real server processes on the build filesystem.

## 8. Packaging, registry, and the agent card

`server.json` carries the registry identity `ai.qompass/meister`,
version 0.2.0, repository and website. Packages are OMITTED:
nothing is published yet, and no package URL or hash is invented;
packages are added at Rung 9 publication.

The agent card (`.well-known/agent-card.json`, A2A v1.0.1) is
the fleet pilot for cards as canonical capability manifests
(D-1605), in the spec-valid fleet profile (D-1607). Meister is
an MCP server over stdio and has NO A2A endpoint; the card
says so without breaking the standard: `supportedInterfaces`
(a required, non-empty field in v1.0) carries exactly one
entry whose `protocolBinding` is the qompass MCP custom
binding URI `https://qompass.ai/extensions/mcp-interface/v1`
— the spec's own route for custom transports — with
`protocolVersion` "1.0" and `url` carrying the stdio command
`~/.local/bin/meister` under that binding's semantics. No
core A2A binding is claimed. The same URI names the
capability extension whose params carry the provisioning
facts (implementation rmcp, registry name, and `invocation`:
stdio transport, command, no args, protocol era 2026-07-28)
so a client config can be generated from the card alone.
Since EFLO-04 the same params carry `profiles` — one whole
invocation entry per declared surface profile (§3), each the
base invocation plus `env: {"MEISTER_PROFILE": "<profile>"}` —
and `defaultProfile` (`core`), the profile the bare invocation
launches. A client config can therefore be generated per
profile from the card alone. The card still declares exactly
one interface: profiles are launch variants of the one MCP
server, not further interfaces. `server.json` stays
single-identity and names no profile.
Correction of record: the card was born with an empty
`supportedInterfaces` and a `stateTransitionHistory` field
that v1.0 removed — neither spec-valid. Both were corrected
the same day, after the authoring standard was verified
against the primary spec sources; the manifest-agreement
tests now pin the corrected profile.

Maintained invariant: card and server.json agree exactly on the
join keys — card `name` == server.json `title`, card `version`
== server.json `version`, extension `registryName` ==
server.json `name`; and the card's profile entries equal the
server's declared profiles — same names, same order, none
missing, none extra, none twice, each entry launching the
profile it names. The invariant is held by
`tests/manifest_agreement.rs`, which reads the declared list
from the built binary and launches every card entry; any change
to one side that breaks it fails the gate.
